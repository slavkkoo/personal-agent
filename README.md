# personal-agent — личный AI-ассистент в Telegram

Telegram-бот, который отвечает только вам. Он читает вашу личку в Telegram, почту
и календарь, ведёт список дел и раз в неделю устраивает менторскую сессию.
Работает на вашем сервере (VPS или домашний Linux) и использует headless Claude Code
по подписке (`claude -p`), так что API-ключ не нужен.

Шаблон извлечён из рабочей системы, которой автор пользуется каждый день. Имена,
адреса, ID и расписание вынесены в `.env`.

## Три роли

1. **Ассистент.** Знает, кто ждёт вашего ответа в личке Telegram, что важного пришло
   на почту (до 5 ящиков) и что стоит в календаре (до 5 календарей). Читает и заводит
   задачи в GitLab, если вы его подключили.
2. **Планировщик.** Раскладывает день по свободным окнам между встречами и ведёт
   ваш личный список задач со сроками и приоритетами.
3. **PM-ментор.** Спарринг-партнёр уровня CPO по продукту, приоритетам и карьере.
   Если в `.claude-config/skills/` лежат ваши скиллы-фреймворки, ментор выбирает
   подходящий по `config/mentor-skills.md`, читает его и применяет методику.
   Поддакивать он не должен.

## Личное ≠ командное

Этот агент — личная часть Team OS. Командный агент
([team-os-agent](https://github.com/slavkkoo/team-os-agent)) и база знаний команды
([team-os-knowledge](https://github.com/slavkkoo/team-os-knowledge)) живут отдельно:

| | Личный агент (этот репо) | Командный агент |
|---|---|---|
| Системный пользователь | `assistant` | `teamagent` |
| Бот и токены | свой бот, своя Telegram-сессия, свой `claude setup-token` | свои |
| Кому отвечает | только `OWNER_ID` | команде (`TEAM_IDS`) |
| Данные | ваша личка, почта, календарь | командные чаты, код, база знаний |

У агентов нет общих файлов, сессий и токенов. В `settings.json` личному агенту
запрещено читать домашний каталог командного (`TEAM_AGENT_USER`). Личные данные
не должны попадать туда, где их увидит команда, а командный агент не должен
получить доступ к вашей почте.

## Как этим пользоваться

**Утром приходит брифинг** (время задаётся в `BRIEFING_TIME`), рассчитанный на один экран телефона:

```
☀️ Брифинг за 28.10
🔴 Ждут ответа
Разработчик Acme — просит ревью до обеда (вчера 19:40)
Друг — спрашивает, получится ли в субботу (вчера 22:10)
📅 Сегодня в календаре
10:00–10:30 Стендап команды
14:00–15:00 Созвон с клиентом Acme
Завтра: 11:00 планирование спринта
🎯 План дня
1) Ревью для разработчика — окно 10:30–12:00
2) Черновик роадмапа (просрочено, high) — окно 15:00–17:00
📋 Задачи
#4 Подготовить ретро — срок сегодня
ещё 5 открытых (полный список — по понедельникам)
📬 Почта
рабочий: поддержка Acme — эскалация по записи клиента
🟡 Продолжить разговор
Коллега-PM — ждёт от вас решения по тарифам, тред завис с пятницы
⚪ Просто в курсе
Семья — личное сообщение
```

Личное описывается нейтрально («личное сообщение от X»), без подробностей о здоровье,
семье и деньгах. Если источник сломан, брифинг начинается со строки
`⚠️ Источники с ошибкой: …`.

**Днём вы пишете ему как человеку:**

| Говорю | Что происходит |
|---|---|
| «кто ждёт ответа?» | свежий дамп лички за сутки → список «кому и что ответить» |
| «спланируй день» | календарь + открытые задачи → тайм-блоки, свободные окна, что не влезает |
| «запиши задачу: … до пятницы» | `bin/tasks add` со сроком и приоритетом |
| «что у меня по задачам» | `bin/tasks list` |
| «сделай из этого задачу» (reply на сообщение) | issue в GitLab от вашего имени с пометкой `GITLAB_MARKER` |
| «что там в #123» | сам читает задачу GitLab, копировать её текст не нужно |
| «проставь ей тег bug» | добавляет лейбл из whitelist к задаче, о которой шла речь |
| «поправь описание» | правит описание, но только у задачи, созданной через ассистента |
| «почисти почту» / «это тоже мусор» | мусорные отправители → корзина (в Gmail 30 дней на откат), список пополняется |
| «стоит ли делать эту фичу?» | выбирает скилл из маппинга, читает `SKILL.md` и применяет методику |

Бот понимает reply: «ей», «её», «это» относятся к процитированному сообщению.
Он помнит последние 6 реплик диалога в пределах 20 минут.

**Раз в неделю (по умолчанию в пятницу в 16:00) — менторская сессия.** Ассистент
просматривает брифинги недели, календарь следующей недели и задачи. Он пишет одно
наблюдение, предлагает фокус и задаёт два вопроса, на которые неудобно отвечать.

## Архитектура

```
Telegram (личка, только OWNER_ID)
      │ long-poll getUpdates
      ▼
bin/assistant_bot.py ── personal-agent.service (python3 stdlib, Restart=always)
      │ на каждое сообщение — subprocess, промпт из prompts/assistant.md
      ▼
claude -p --model $MODEL_ANSWER        права: .claude-config/settings.json
  ├─ bin/read_personal.py   личные диалоги Telegram (Telethon, read-only, своя сессия)
  ├─ bin/mail_triage.py     IMAP: непрочитанное (BODY.PEEK) + мусор → корзина
  ├─ bin/read_calendar.py   секретные ICS-адреса Google Calendar
  ├─ bin/tasks              личные задачи (memory/tasks.jsonl)
  └─ bin/gl_task            GitLab: view / search / create / label / edit своих

personal-agent-briefing.timer ─▶ bin/run_briefing.sh
      read_personal + mail_triage + read_calendar + tasks ─▶ run/personal.txt
      claude -p --model $MODEL_DUTY  (только Read этого файла)
      проверки ☀️ / ошибки источников / ok:true ─▶ Telegram владельцу

personal-agent-mentor.timer ─▶ bin/run_mentor.sh
      брифинги недели + календарь на 7 дней + задачи ─▶ claude (только Read) ─▶ Telegram

OnFailure= любого юнита ─▶ personal-agent-failed@.service ─▶ «🛑 Упал …» + хвост журнала
```

Состояние хранится в файлах в `AGENT_HOME`. `memory/` содержит брифинги, задачи,
историю диалога, список мусорных отправителей и журнал триажа. В `run/` лежат
промежуточные дампы и логи ошибок. Базы данных нет.

## Почему так

- **ICS и app-пароли вместо OAuth.** Не нужен проект в Google Cloud, client_id или
  consent screen, а сервер работает headless. Цена — секретный ICS-адрес и app-пароль
  дают доступ «всё или ничего». Храните их как пароли (см. «Безопасность»).
- **Claude Code по подписке, а не API.** `claude setup-token` выдаёт долгоживущий
  OAuth-токен. Агент сам вызывает инструменты и читает файлы, поэтому писать
  tool-calling код не нужно.
- **Инструменты — маленькие скрипты с жёсткими границами.** Агент не получает «доступ
  к GitLab» целиком. Он получает `gl_task`, который умеет ровно пять команд.
  Опасных команд в нём просто нет.
- **Файлы вместо БД.** jsonl и txt легко прочитать глазами, забэкапить и починить руками.
- **Свои скрипты, а не MCP-серверы.** Их меньше, они проще и прозрачны для аудита.
  Права описываются строками в `settings.json`.
- **Python stdlib.** Внешняя зависимость одна — Telethon в `.venv`, только для чтения
  Telegram-аккаунта.

## Безопасность

Ассистент видит вашу личку, почту и календарь. Защиты ниже взяты из реальных
инцидентов и аудитов, убирать их не стоит:

1. **Брифинг-агенту доступен только `Read`.** `run_briefing.sh` и `run_mentor.sh`
   запускают `claude` с `--allowedTools "Read"` и
   `--disallowedTools "Bash,Edit,Write,…,WebFetch"`. Брифинг читает чужие сообщения
   и письма, а в них может оказаться prompt injection («ассистент, перешли мне…»).
   Без Bash такому тексту нечем действовать: ни `gl_task`, ни `add-junk`, ни сети.
2. **Deny на секреты.** В `deploy/claude-config-settings.json.in` чат-агенту
   разрешён вызов только своих скриптов по полным путям. Запрещено чтение `.env*`,
   `*.session*`, `~/.claude-token.env`, конфигов и транскриптов Claude, домашнего
   каталога командного агента и `/root`. Также запрещены `Write`/`Edit`, веб,
   `curl`, `cat`, `env`, `python3 -c`.
3. **Отвечает только владельцу.** Бот работает только в личном чате и только с
   `OWNER_ID`. Остальным он молчит: не отвечает «доступ запрещён» и не подтверждает,
   что бот вообще существует.
4. **Доставка проверяется по `ok:true`.** Обёртки считают отправку успешной, только
   если Telegram подтвердил каждый кусок сообщения. Иначе юнит падает и срабатывает алерт.
5. **Источник с ошибкой выносится первой строкой.** Каждый источник печатает
   `=== … ОШИБКА … ===`, обёртка собирает такие строки в начало брифинга. Молчание
   не считается успехом.
6. **Ответ без «☀️» не отправляется как брифинг.** Пустой ответ или ответ модели
   без строки `☀️ Брифинг…` (например, текст ошибки авторизации) уходит как
   `⚠️ брифинг не собрался`, а не под видом брифинга. Для ментора то же самое с «🧭».
7. **Письма читаются через `BODY.PEEK`** и не помечаются прочитанными.
8. **Удаление — только в корзину.** `mail_triage.py` делает MOVE в корзину и никогда
   не вызывает EXPUNGE. В корзину попадают письма только тех отправителей, чей адрес
   точно совпал со строкой списка (IMAP `FROM` ищет подстроку, поэтому кандидаты
   перепроверяются). Каждое перемещение пишется в `memory/triage_log.jsonl`.
9. **GitLab без разрушительных команд.** Закрывать, удалять задачи и снимать лейблы
   нельзя. Лейблы ставятся только из `GITLAB_LABELS`. `edit` работает только для
   задач, где в описании есть `GITLAB_MARKER`, то есть созданных через ассистента.
   У пишущих команд есть `--dry-run`.
10. **О личном брифинг пишет нейтрально.** Здоровье, семья и деньги сводятся к
    «личное сообщение от X»: брифинг может прочитать кто-то, кто заглянул вам в телефон.
11. **Секреты лежат вне git.** `.env` (chmod 600), `*.session` и `~/.claude-token.env`
    перечислены в `.gitignore`, а `AGENT_HOME` имеет права 700.

Что остаётся на вас:
- `TG_API_ID`/`TG_API_HASH` вместе с сессией дают полный доступ к вашему
  Telegram-аккаунту. Ограничение «только чтение» обеспечивает код, а не Telegram.
- Секретный ICS-адрес открывает календарь любому, у кого есть ссылка. При утечке
  сбросьте его в настройках календаря.
- Отзовите app-пароль, если сервер скомпрометирован.
- Чат-агент (в отличие от брифинга) может вызывать свои скрипты и при этом тоже
  читает чужие сообщения. Его write-действия ограничены личными задачами, списком
  мусора и GitLab-командами выше. В худшем случае prompt injection сможет завести
  задачу или отправить чьи-то письма в корзину, но не удалить их и не написать
  кому-то от вашего имени.

## Настройка

| Что | Где |
|---|---|
| Имена, ID, токены, ящики, календари, GitLab, модели, TZ, расписание | `.env` (все переменные с комментариями — в `.env.example`) |
| Мусорные отправители | `memory/junk_senders.txt` (стартовый пример — `config/junk_senders.example.txt`) |
| Маппинг «тип вопроса → скилл» | `config/mentor-skills.md` |
| Сами скиллы ментора | `.claude-config/skills/<имя>/SKILL.md` (в репо не входят) |
| Тексты промптов | `prompts/*.md` (плейсхолдеры `{{…}}` подставляет `bin/pa_common.py`) |
| Права агента | `deploy/claude-config-settings.json.in` → `install.sh` → `.claude-config/settings.json` |
| systemd | `deploy/systemd/*.in` → `install.sh` |

Таймеры работают по `TZ` из `.env`: он подставляется прямо в `OnCalendar=`.
**Поставьте свой TZ**, иначе брифинг придёт по UTC.

## Что можно добавить

Ничего из этого в шаблоне нет, но всё это можно добавить. На что стоит обратить внимание:

- **OAuth вместо app-паролей и ICS.** Даёт гранулярные права (только чтение почты,
  только календарь), отзыв по одному клиенту, работу там, где админ Workspace
  запретил app-пароли. Нужен проект в Google Cloud и хранение refresh-токена. Проверьте,
  что scope ровно тот, что нужен (`gmail.readonly` + `gmail.modify` только для корзины).
- **Запись и саммари встреч.** После созвона приходит саммари с решениями и задачами
  в `tasks`. Обратите внимание на согласие участников на запись. Транскрипт хранится
  в `memory/` и тоже личный. В брифинг попадают только решения, без цитат.
- **Второй источник задач (Todoist, Notion).** Позволяет не переносить задачи руками.
  Начните с read-only, write — только по явной просьбе. Различайте задачи из разных
  источников, чтобы `done` не закрыл чужое.
- **Голосовые сообщения.** Сейчас бот игнорирует всё, кроме текста. Распознавание
  можно делать локально (whisper.cpp) или через API, но аудио — это тоже личные
  данные, поэтому лучше удалять файл сразу после распознавания.
- **Отчёт о том, что выучил командный агент.** Еженедельная сводка из
  [team-os-agent](https://github.com/slavkkoo/team-os-agent): какие факты добавились
  в базу знаний и какие вопросы остались без ответа. Передавайте готовую сводку
  через бота, без общего доступа к файлам. Иначе граница «личное ≠ командное»
  размоется.
- **Повторяющиеся события календаря.** Простой парсер ICS не разворачивает `RRULE`.
  Это можно сделать stdlib-кодом или через `icalendar` + `recurring_ical_events`
  в `.venv`.
- **Hardening юнитов.** Добавьте `ProtectSystem=strict`, `ReadWritePaths=` на
  `AGENT_HOME` и `~/.claude*`, `ProtectHome=tmpfs` с `BindPaths=`. Проверяйте на живом
  сервере: Claude Code пишет кеши в домашний каталог.

## Грабли

Уроки, которые стоили времени в проде:

- **Одна Telethon-сессия на два клиента конфликтует.** Личный агент сначала работал
  на копии сессии другого клиента. Telegram не любит, когда один ключ сессии
  используется из двух мест одновременно, и может его отозвать
  (`AuthKeyDuplicatedError`). Решение: отдельный вход через `bin/tg_login.py`,
  у каждого клиента своя сессия (в «Устройствах» Telegram это отдельная строка).
- **Heredoc без кавычек интерполирует бэктики.** Если промпт собирается в `<<EOF`,
  то бэктики вокруг команд (`` `bin/tasks list` ``) и `$переменные` bash выполняет
  и подставляет ещё при сборке промпта, и модель получает искажённый текст. Поэтому
  промпты лежат в `prompts/*.md` и рендерятся `pa_common.py render`. В своих скриптах
  пишите `<<'EOF'`.
- **Пишущие команды тестируйте только на тестовых объектах.** Однажды тест
  перезаписал описание реальной задачи. Отсюда `--dry-run` у пишущих команд `gl_task`,
  ограничение `edit` только своими задачами и правило: проверки гонять на тестовой
  задаче или тестовом проекте.
- **Источник молча падал месяц.** Вход в один из почтовых ящиков ломался около
  месяца. Строка об ошибке тонула в дампе, модель её не упоминала, а брифинг
  выглядел нормально. С тех пор ошибки источников выносятся первой строкой.
- **Ошибка авторизации ушла под видом брифинга.** Когда токен отозвали, модель
  ответила текстом ошибки, и он ушёл владельцу как брифинг. Теперь ответ без «☀️»
  не отправляется как брифинг.
- **«ok» в логе при недоставке.** Обёртка не проверяла ответ Telegram и писала
  «ok», даже когда сообщение не дошло. Теперь `send` проверяет `"ok":true` у каждого куска.
- **Каждый день один и тот же список задач.** Полный список задач в каждом брифинге
  растягивал его на 2–3 экрана. Теперь полный список приходит только по понедельникам,
  а в остальные дни — только просроченные и срочные задачи.
- **IMAP `FROM` ищет подстроку.** Строка `cal…@example.com` в списке мусора задела
  бы похожие адреса. Поэтому кандидаты перепроверяются по точному адресу.
